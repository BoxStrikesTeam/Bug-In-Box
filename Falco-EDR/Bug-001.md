# BUG-001: Untrusted Search Path (CWE-426) in Falco's Kernel Module Loading Fallback

**Researched by:** Eneshan Erdoğan Karaca

**Team:** BoxStrike Team

**Target:** [Falco](https://github.com/falcosecurity/falco) (CNCF project)

**Status:** Fixed — see [falcosecurity/falco#3943](https://github.com/falcosecurity/falco/pull/3943)

**Classification:** Low severity / hardening (per Falco maintainers)

**CVE / GHSA:** None assigned — classified by the Falco team as a defense-in-depth

hardening fix rather than a security advisory

> ⚠️ **This write-up was held back at the maintainers' request until the fix
> merged.** Responsible disclosure was coordinated with the Falco security
> team via `cncf-falco-maintainers@lists.cncf.io`.

---

## Summary

While auditing Falco's userspace code for the kernel-module ("kmod") engine,
BoxStrike Team identified that the fallback path responsible for loading the
Falco kernel module resolved the `modprobe` binary via the process's `PATH`
environment variable rather than a fixed, trusted absolute path. This is an
instance of **CWE-426: Untrusted Search Path**.

In deployment scenarios where an attacker can influence the `PATH` inherited
by the Falco process (or write to a directory that precedes the legitimate
`modprobe` location in it), this could result in an attacker-controlled
binary being executed with the privileges of the Falco process — typically
**root**, since the kmod engine requires root / `CAP_SYS_ADMIN`.

## Where it was found

**File:** `userspace/falco/app/actions/helpers_inspector.cpp`
**Function:** `open_live_inspector()`

```cpp
} catch(sinsp_exception& e) {
    // Try to insert the Falco kernel module
    falco_logger::log(
            falco_logger::level::INFO,
            "Trying to inject the Kernel module and opening the capture again...");
    if(system("modprobe " DRIVER_NAME " > /dev/null 2> /dev/null")) {
        falco_logger::log(falco_logger::level::ERR, "Unable to load the driver\n");
    }
    inspector->open_kmod(s.syscall_buffer_bytes_size, s.selected_sc_set);
}
```

`DRIVER_NAME` is defined at build time (`CMakeLists.txt`) as `"falco"`, so this
expands to:

```c
system("modprobe falco > /dev/null 2> /dev/null")
```

`system()` invokes `/bin/sh -c`, and since `modprobe` is unqualified (no
absolute path), the shell resolves it by searching every directory listed in
`PATH`, in order, until a match is found. This is the same class of bug
behind many historical local-privilege-escalation issues: whoever controls
an earlier-searched, writable directory controls what actually runs.

This branch is only reached when the initial `inspector->open_kmod(...)`
call throws — i.e. when the Falco kernel module isn't already loaded at
startup.

## Why this matters (and why it doesn't, in the default install)

- **Default / systemd-managed installs are not affected.** Falco's
  maintained `falco-kmod-inject.service` systemd unit pre-loads the module
  using an absolute path (`/sbin/modprobe falco`) *before* Falco starts, as a
  `Requires=` dependency. In that flow, `open_kmod()` normally succeeds on
  the first attempt and this fallback is never reached. systemd also assigns
  its own default `PATH` to the unit rather than inheriting an
  attacker-influenced one.
- **The precondition is non-trivial.** Exploiting this requires the attacker
  to already control (or write to a directory ahead of `/sbin` in) the
  `PATH` of the process that will eventually run Falco — access that is, in
  practice, close to the level of privilege the bug would grant. We
  deliberately did not inflate the severity here: this is best described as
  a hardening / defense-in-depth issue, not a remotely or trivially
  exploitable vulnerability in a default deployment.
- **Reachable in non-default deployments:** manual invocations, container
  entrypoints or base images with a custom `PATH`, packaging/post-install
  scripts, or any scenario where the module is unloaded at runtime and
  Falco restarts outside the hardened systemd unit.

## Proof of concept

We isolated the exact vulnerable statement to demonstrate the resolution
behavior without needing to reproduce a full kernel-module failure:

```cpp
// verbatim reproduction of the vulnerable call
#define DRIVER_NAME "falco"
system("modprobe " DRIVER_NAME " > /dev/null 2> /dev/null");
```

With an attacker-controlled directory prepended to `PATH`, containing an
executable named `modprobe`:

```bash
mkdir -p /tmp/attacker_controlled_dir
cat > /tmp/attacker_controlled_dir/modprobe << 'EOF'
#!/bin/bash
echo "[PWNED] malicious 'modprobe' executed instead of the real one"
echo "Running as: $(whoami) (uid=$(id -u))"
EOF
chmod +x /tmp/attacker_controlled_dir/modprobe

export PATH="/tmp/attacker_controlled_dir:$PATH"
# ... running the vulnerable call here executes the attacker's script
```

Result: the attacker-controlled script executed with the privileges of the
calling process, confirming the resolution happens via `PATH` rather than a
fixed location.

## The fix

Falco maintainers agreed with our root-cause analysis and severity
assessment. The fix, submitted as
[falcosecurity/falco#3943](https://github.com/falcosecurity/falco/pull/3943),
replaces the `system()`/shell invocation with a direct `fork()` + `execl()`
call against a small, fixed set of absolute paths (`/usr/sbin/modprobe`,
`/sbin/modprobe`), eliminating both the shell and the `PATH` dependency
entirely. Since no user-controlled input was ever interpolated into the
original call, there was no need for shell semantics in the first place.

During review, Falco maintainer **@leogr** also caught two issues in our
initial patch that we want to credit here:
1. The POSIX-only APIs we introduced (`fork()`, `waitpid()`, `WIFEXITED()`,
   `<sys/wait.h>`) aren't available on Windows/MSVC, and this file compiles
   on all platforms — the fix needed to be gated behind `#ifdef __linux__`.
2. `waitpid()` can return `EINTR` if a signal lands mid-wait (Falco's
   metrics timer installs `SIGALRM` without `SA_RESTART`), which needed a
   retry loop to avoid a spurious "unable to load the driver" log.
